# 発注書 第7便: 移動の引っかかりを直す(ヌルヌル歩ける当たり判定)

ユーザー報告(2026-08-10 夜、実機プレイ): 「道があるのに進めない場所がある。特に角をまがったりするときにつっかかったりして、操作感がいまいち。ヌルヌル進めるようにして欲しい」

## 1. 目的・変更対象・スコープ外

**目的**: 壁への接触で急停止・引っかかりが起きるのをなくし、通路に沿って滑るように歩けるようにする。あわせて「床が見えているのに立ち入れない場所」を解消する。

**変更してよいファイル**:
- `src/maze.js` — 通行判定(`isInsidePassage` / `canStandAt` 周辺)
- `src/main.js` — `updatePlayer` の移動解決部分(204-205 行の x/z 別判定)
- `test/` — 新規テストファイルの追加、既存テストへの追記

**スコープ外(気づいても触らない)**:
- `src/render3d.js` の見た目・床メッシュ生成。今回は「見えている床に立てるようにする」側を判定に合わせる。床の形は変えない
- 通路半径の定数変更: `STROKE_RADIUS = 1.7` / `BRIDGE_RADIUS = 0.95` / `HARAI_END_RADIUS = 0.9` / `PLAYER_RADIUS = 0.45` は変えない。橋が細いのは確定仕様(`docs/game-design.md:14`「離れたパーツの間をつなぐ通路 = 細い道」)、はらいの先細りも第4便の確定仕様
- `MOVE_SPEED` / `TOUCH_TURN_SPEED` の変更(操作感が足りなければ選択肢として提案するに留める)
- `src/village.js` / `src/ui.js` / 迷路生成アルゴリズム / スコア

## 2. 制約

- simplicity 優先。物理エンジンの導入や当たり判定の全面書き換えはしない。既存の「カプセル(線分 + 半径)の和集合が通路」というモデルを維持したまま、判定と移動解決だけを直す
- **性能**: iPad 実機で 60fps を維持する。`isInsidePassage` は `maze.strokeSegments` を毎回線形走査している(空間インデックスなし。`src/render3d.js:461` の `PassageIndex` は描画専用)。判定呼び出し回数を増やすなら、早期 return・AABB 事前判定・最寄り線分のキャッシュなどでコストを相殺すること
- **方向規約は変えない**: three.js カメラ前方 = `(-sin(yaw), -cos(yaw))`。既存コメント(`src/main.js:199-200`)の通り
- 設計判断(円のサンプル点数・スライドの優先順位・サブステップ幅など)で迷ったら、実装で勝手に確定せず選択肢と根拠を acceptance packet に書いて返す
- commit / push はしない(公開は Pages 自動反映なので、検収前に push されると子どもが遊ぶ版が壊れる)

## 3. 関連 incident・同型事故

- 当たり判定そのものの事故記録は `docs/` に未記録(今回が初出)

## 4. 検収 oracle

(a) `node --test` で既存 `test/maze-gen.test.mjs` が全通過すること

(b) 新規テストで以下が通ること。**各ケースは修正前に落ちることを先に確認**し、回帰テストとして固定する:
1. **内側の角**: 直交する 2 本の画(例: A = (-10,0)→(0,0)、B = (0,0)→(0,10))で、点 (1.3, 1.3) に立てること。この点はプレイヤー円(半径 0.45)が A∪B に完全に収まるので床は連続しているが、現行判定はどちらの画からも `1.7 - 0.45 = 1.25` を超えるため弾かれる
2. **斜めの壁で滑る**: 世界軸に平行でない画(例: 37 度)に対し、壁へ斜めに突っ込む入力を与えたとき、1 フレームの移動量が 0 にならず、画の方向へ成分が残ること。真正面(法線方向)から突っ込んだ場合のみ停止してよい
3. **回転後も同じ**: `rotateStrokes` で 0/37/90/143/270 度に回した同一の画で、上記 1・2 が同じように成立すること(軸平行のケースだけで通らないことの担保)
4. **押し戻し**: 通路の外にプレイヤー座標を置いた状態から、数フレームで通路内に復帰できること(現行は永久に動けない)
5. **壁抜けしない**: `delta` を極端に大きく(例: 0.5 秒)しても、移動後の座標が必ず `canStandAt` を満たすこと

(c) **性能の実測を acceptance packet に書く**: 1 フレームあたりの線分距離計算の回数を現行版と新版で比較した数値(実測または理論値 + 実測の裏取り)。10 倍を超えるなら緩和策を入れるか、選択肢として報告する

(d) 橋(`BRIDGE_RADIUS = 0.95`、実効の通り幅 1.0)の上を、中心線から少しずれた角度で進入しても弾かれずに渡れること。橋は細いまま(細さは仕様)だが、縁に触れたら滑って乗り続けられるようにする

## 現状の診断(Claude 調べ。前提にしてよいが、各自で検証すること)

1. **通行判定が画を 1 本ずつ独立に見ている**(`src/maze.js:369-385`)。`isInsidePassage(x, z, clearance)` は各線分について「半径 - clearance」以内かを見て、1 本でも満たせば true を返す。`canStandAt` は `clearance = PLAYER_RADIUS`。これは「プレイヤー円が **1 本の画の中** に収まるか」であって、「床(画の和集合)の中に収まるか」ではない。画が交わる内側の角では、床は連続して見えるのに判定に穴があく
2. **移動解決が x/z 別判定**(`src/main.js:204-205`)。世界軸に平行な壁でしか滑らない。第5便で入れた回転出題(`roundRotation` / `rotateStrokes`)で通路がほぼ全部斜めになったため、壁に触れるとほぼ常に急停止する。これが「つっかかる」の主因と見ている
3. **細い箇所での余裕のなさ**: 実効の通り半径は 画 1.25 / 橋 0.5 / はらい先端 0.45。細い場所ほど 1・2 の影響が体感で効く
4. **押し戻しがない**: 何らかの理由で通路外に出ると `canStandAt` が全方向 false になり、完全に動けなくなる

## 実装方針(案。より良い案があれば選択肢で返してよい)

1. **通行判定を和集合ベースに**: プレイヤー円の中心 + 円周上 K 点(8〜12 点程度)を `isInsidePassage(..., clearance = 0)` で判定し、全点が床内なら立てる、とする。これで内側の角が開通する。K と性能のトレードオフは実測して決める
2. **collide & slide**: 希望移動量 d に対し、①そのまま通れるか ②通れなければ最寄り線分の向き(接線)へ d を射影して再挑戦 ③それも駄目なら現行の x/z 別判定 ④最後に半分の歩幅、の順に試す。②が「ヌルヌル」の本体
3. **サブステップ**: 1 フレームの移動を最大歩幅(例 0.15)以下に分割して繰り返す。壁抜けと角での引っかかりの両方に効く
4. **押し戻し**: フレーム開始時に `canStandAt` が false なら、最寄り線分の中心線へ向けて少し押し戻す
